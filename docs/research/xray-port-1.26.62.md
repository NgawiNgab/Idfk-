# Apollon-style ore outlines for LeviLauncher — Minecraft 1.26.62

**Status:** [Host core](../../README.md#host-only-outline-core) and [CI-packaged synthetic HUD test](../../README.md#offline-hud-smoke-test) implemented. User confirmed synthetic HUD drawing, the diamond filter, and toggle-off clearing on device. A [separate Script API probe](one-block-world-probe.md#device-result) established the on-device reference block values. The [native chunk scheduler](chunk-scanner.md) passes multi-chunk host fixtures; there is no native world reader. Minecraft `1.26.62` is user-reported. The [device-reported loaded Build ID](intake.md#loaded-build-id) matches the separate Drive sample; full-file equality is unverified. [XRAY-001](xray-001-evidence.md) reports a lookup candidate; [XRAY-002](xray-002-evidence.md) explains a related 64-bit comparison. Neither validates a native call or layout.

## First version

Port the visible behavior of Apollon's `xrayDefault` path: a toggle and ore category filters with colored outlines over nearby selected blocks in an offline test world. Keep the HUD separate from terrain rendering. Do not port the FullBright patch, Xray Camera, Xray Caves, or a forced terrain rebuild. Do not ship Apollon source or the Minecraft library in the mod.

- **CONFIRMED — Apollon source:** [The source trace](apollon.md#acquisition--classification--rendering) shows collection in `Block_getRenderLayer`, a cached list of positions and colors, and an ImGui overlay. The collection hook forwards the original layer. Its offsets and projection conventions are not a contract for `1.26.62`.
- **CONFIRMED — BedrockTools source:** [Light Overlay](intake.md#bedrocktools-reference) uses a coordinate-based block lookup for a different visual effect. Its tick event and region wrapper are examples of integration, not verified bindings for this build. The pinned source has no portable public `BlockSource::getBlock` method. [Cinematic Camera](https://github.com/NgawiNgab/BedrockTools/blob/c03d3ae0c9022557de0acdf0d94e373e0b9e0579/src/modules/visual/cinematiccamera.cpp#L152-L197) shows how it gets HUD size, submits draw commands, and clears them when inactive.
- **CONFIRMED — Preloader source at `cc08b40a31471d3e2dedb267f5f17b28da2b0604`:** [`PL_REGISTER_MOD`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/include/pl/Mod.hpp#L314-L338) exports a lifecycle registration. The [manifest parser](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/internal/ModManifest.cpp#L83-L141) expects a `preload-native` `manifest.json` and `.so` entry. The public Mod Menu API includes [`DrawCommandType::Line`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/include/pl/ModMenu.hpp#L74-L85), [`submitDrawCommands()` and `getHudSurfaceSize()`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/include/pl/ModMenu.hpp#L176-L219). These APIs make a launcher HUD preferable to copying Apollon's ImGui/JNI surface, subject to checking the user's Preloader revision and measuring the draw-command budget.

## Launcher and HUD compatibility

**Question:** Which parts of the port can use the public launcher APIs without depending on Minecraft internals? The findings here apply to [LeviLauncher-Android `d544df8`](https://github.com/LiteLDev/LeviLauncher-Android/tree/d544df8cafab731ba7686dfb88951602f13293ef), whose `app/src/main/cpp/preloader` gitlink pins `cc08b40`. Neither revision is established for the user's installation.

| Classification | Source evidence and design implication |
| --- | --- |
| **CONFIRMED — packaging example** | The launcher's [`full-cpp-mod` example](https://github.com/LiteLDev/LeviLauncher-Android/blob/d544df8cafab731ba7686dfb88951602f13293ef/examples/full-cpp-mod/README.md#L7-L17) shows lifecycle, typed defaults, and Mod Menu registration. [`build.ps1`](https://github.com/LiteLDev/LeviLauncher-Android/blob/d544df8cafab731ba7686dfb88951602f13293ef/examples/full-cpp-mod/build.ps1#L141-L183) packages a ZIP named `.levipack` with a root `manifest.json`, the entry `.so`, and a `config/` directory. Use that package shape, not either reference's game bindings. Verify exported symbols and ELF dependencies against the chosen Preloader before any device test. |
| **CONFIRMED — screen-space line contract** | [`HudOverlay.onSizeChanged`](https://github.com/LiteLDev/LeviLauncher-Android/blob/d544df8cafab731ba7686dfb88951602f13293ef/app/src/main/java/org/levimc/launcher/core/mods/inbuilt/overlay/HudOverlay.java#L293-L297) forwards the View dimensions. [`HudOverlay.onDraw`](https://github.com/LiteLDev/LeviLauncher-Android/blob/d544df8cafab731ba7686dfb88951602f13293ef/app/src/main/java/org/levimc/launcher/core/mods/inbuilt/overlay/HudOverlay.java#L751-L760) draws a line from `(x, y)` to `(x + w, y + h)` for ordinary pixel coordinates, using `size` as stroke width. It also interprets certain negative coordinates as anchors. Clip to the positive-size HUD before submission, and don't pass game coordinates or copy Apollon's ImGui color/coordinate conventions. The HUD View is not evidence of the game camera or viewport. |
| **CONFIRMED — batch replacement and limits** | [`SubmitCppDrawCommands`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/runtime/ModMenuBridge.cpp#L686-L726) validates then copies a batch into module-owned storage, replacing it with no commands if the input is empty. [`ValidateDrawCommands`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/runtime/ModMenuBridge.cpp#L453-L479) rejects non-finite geometry and counts over the [4,096-command limit](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/runtime/ModMenuBridge.cpp#L29-L44) before replacement, leaving old commands intact. [`GetDrawCommands`](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/runtime/ModMenuBridge.cpp#L1197-L1210) delivers enabled modules only, but [toggling the module](https://github.com/LiteLDev/preloader-android/blob/cc08b40a31471d3e2dedb267f5f17b28da2b0604/src/pl/runtime/ModMenuBridge.cpp#L962-L985) does not erase its batch. Submit an empty batch when context becomes invalid or the feature is disabled so old outlines do not return on re-enable. Enforce a smaller measured budget; the source limit is not a performance target. |
| **USER-REPORTED — basic installed HUD support** | Both synthetic boxes appeared on the installed launcher. The diamond filter and module-off clearing behaved as expected. Resize, package unload, device frame cost, and game-to-HUD viewport mapping remain untested. See the [smoke observation](bedrocktools-integration.md#what-the-ci-result-means). |

## Implementation plan and gates

| Area | Plan | Required evidence or check |
| --- | --- | --- |
| Loader and configuration | Start with a standalone C++ Android `arm64-v8a` `.levipack` using the Preloader lifecycle. Register a default-off toggle and ore category/range settings. Use BedrockTools as a reference, not a required dependency. | Verify the installed launcher/Preloader supports registration and HUD submission. Keep the game-data adapter inactive on an unsupported or unknown game build. |
| World acquisition | Try the [passive pre-cull terrain probe](passive-terrain.md) first. It forwards existing calls and observes values, with no additional lookup or changed render-layer decision. Keep the fixture-tested [scheduler](chunk-scanner.md) as a fallback. | Establish exposed and enclosed coverage during ordinary builds on device. Then verify world and section lifetime, invalidation, and unannounced nearby results. For the fallback, identify a render-ready feed and a non-generating, independently guarded reader. The [XRAY-003 predicate](xray-003-evidence.md) does not guard loadedness. |
| Classification and cache | Map verified block identifiers to ore categories and colors. Keep an index by world, dimension, and block coordinate. Copy only values into a bounded render snapshot; revalidate non-air replacements, and clear on disable, world change, or invalid context. | Compare vanilla and deepslate variants plus unrelated and unavailable blocks in a controlled world; do not assume Apollon's `tile.*` strings are canonical here. |
| Projection and presentation | Project outline edges using a verified camera snapshot and submit a capped line batch to the launcher HUD. Clip near-plane/offscreen edges; omit duplicate/shared segments where appropriate. | Verify camera convention and safe sampling point, game viewport versus HUD coordinate space, resize/orientation, and safe clearing. Measure lookups per tick, draw commands, and frame cost on device. |

**Implemented without a local hash:** `make test` exercises portable C++20 classification, signed chunk coordinates, bounded cache replacement and reset, homogeneous clipping, edge deduplication, and a capped line batch. The [HUD test](../../README.md#offline-hud-smoke-test) supplies copied fixture names and a synthetic camera, and submits lines on menu changes via Preloader. Its ARM64 build and packager follow the relevant [BedrockTools and launcher references](bedrocktools-integration.md). No game addresses or layouts are used. Fixture-based scanning is tested; the live scan adapter and persistent settings are not implemented.

**Current gate:** Test the [separate passive probe](passive-terrain.md#run-on-the-device) in an offline world with the behavior pack off. The exact-build observer is bounded to the exposed and enclosed controls and does not change the original call. A no-build window is inconclusive, not failed buried coverage. Do not wire projection or a persistent cache on this evidence alone.

**Fallback gate:** [XRAY-008](xray-008-evidence.md) shows why an added render-thread scan is not justified. If revisiting the scheduler, establish a render-ready set and a non-generating reader on a verified update path. With the pack off, independently reproduce the [one-block reference results](one-block-world-probe.md#device-result), including the guard-only unavailable control, before native multi-chunk scanning. Neither the reference probe nor the [matched Build ID](intake.md#loaded-build-id) proves a native read contract. Either acquisition route still needs world identity, stale-result removal, coherent main-pass camera/viewport data, and measured device cost.

## Investigation status

### Investigation XRAY-001 — locate one block-lookup candidate

**Report received.** One match for the BedrockTools lookup pattern is reported at `0x10371934`. Caller and callee behavior support a block lookup, but exact native semantics and safe use on the intended installation are not established. The [evidence note](xray-001-evidence.md) separates the user-run output from the independent Drive scan.

### Investigation XRAY-002 — trace the compared value

**Report received.** The helper follows a veneer and returns one 64-bit load. That explains the mechanics of the comparison, not what the key represents. [XRAY-002 evidence](xray-002-evidence.md) distinguishes the observed load from the name-hash hypothesis. Do not treat the field as a verified identifier or read a presumed string layout.

### Investigation XRAY-003 — test the candidate position predicate

**Report received.** The predicate calls indirectly before comparing a stored key against a fixed value. [XRAY-003 evidence](xray-003-evidence.md) rules it out as an independent availability check. The fixed key, indirect target, and unloaded-position behavior remain unverified.

### Investigation XRAY-004 — trace local reads and fallback

**Report received.** [XRAY-004 evidence](xray-004-evidence.md) shows a packed local position and indexed dispatch consistent with a subchunk-like read. Outer bounds/null failures and inner failures route to the same fallback chain. A block result is therefore not by itself an availability signal. The fallback is not identified as air; final storage access, block identity, and thread/lifetime gates remain open.

### Investigation XRAY-005 — storage dispatch and key resolver

**Report received.** [XRAY-005 evidence](xray-005-evidence.md) shows a pointer-presence gate and an indirect reader, not a verified loaded-position check or palette format. The missing registry-field branch is a fail-fast candidate, not a safe fallback. The key resolver retries a fixed key on misses; neither observed key is identified as a canonical block name. Keep unavailable data separate from air and leave native bindings inactive.

### Investigation XRAY-006 — record selection and name-key evidence

**Report received.** [XRAY-006](xray-006-evidence.md) shows a nullable vertical record selector, a storage installation path, and ordered key lookup with string handling. The separate Drive ELF identifies one uniform storage reader, sample air/end stone/diamond/deepslate name keys, and a status-gated acquisition candidate. The sample initializes the coordinate fallback from the air key. This strengthens the decision to keep unavailable distinct from air and to prefer an independently validated coordinate reader over decoding raw palettes. It does not validate device-side name access, block availability, or lifetime.

### Investigation XRAY-007 — corroborate acquisition and name handling

**Report received.** The [XRAY-007 evidence](xray-007-evidence.md) shows the static air-key fallback setup, the normal and deepslate diamond name literals, and a status-gated acquisition path. The previously rejected helper decoded with `range<>`. “Failed lookup” means the coordinate path took a fallback, not that the tool or Minecraft startup failed. The report did not query a live block or diagnose startup timing. Camera evidence, thread/ownership, installed identity, and controlled offline validation remain separate gates.

### Investigation XRAY-008 — world access and camera windows

**Report received and compared.** All eight requested windows (340 decoded instructions) match the separate Drive ELF after formatting normalization. The [evidence note](xray-008-evidence.md) shows a candidate update-to-region call, cache writes during lookup, different status gates depending on the branch, and a path to camera position and matrix data. Those results do not establish full-cache or loaded-module identity, safe independent availability or lifetime, or active render pass and viewport. No additional static batch is pending.
