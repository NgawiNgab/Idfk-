# Native block ESP and chams — Bedrock 1.26.62 ARM64

**HUD trial only.** The [native LeviPack](../../README.md#block-esp--chams-hud-trial) exercises independent launcher toggles, exact identifier matching and projected silhouettes. Its inputs are simulated and never touch game data. [Loaded Diamond Scan 0.2.0 passed the phone's visual and mining checks](diamond-tracer.md#device-result) using the Script API. The passive probe shows that ordinary terrain builds can visit buried ore. Neither result demonstrates a native main-pass camera or a native way to discover ore in already-meshed terrain on demand.

## Implemented in the HUD trial

The [portable projection](../../src/ore_outline/block_esp.cpp) consumes copied, same-world frame and target values. It clips projected cube faces before dividing by perspective W, takes the convex screen silhouette, and triangulates it. The [launcher module](../../src/launcher/block_esp_trial.cpp) submits the solid fills before the thin center-to-target lines in one HUD batch. The depth values clip geometry to the camera volume, not to the terrain. These chams are a HUD overlay, not a material, game-depth or terrain change. The trial caps the batch at eight targets, one line and at most twenty triangles each, plus a status label. It replaces the batch (including empty batches) on settings changes and clears it on disable/unload. It has no frame producer, no offsets, and no hooks.

## What still needs to be wired

The live `.levipack` should install once in Mod Manager, with no `.mcpack`, script injection, per-world activation, or cheats required by the mod. Start with one supported game build, first person in a disposable local Overworld. One player is not proof of a local session.

| Side | Native responsibility |
| --- | --- |
| World update | Obtain an existing-only read of available block data on its owning update path. Keep the availability check and block copy in the same valid scope. Bound the scan to the player's current and eight neighboring columns, up to 32 Y levels initially. Cap work per update and resume later; never request a chunk, generate terrain, or dirty meshes to fill a gap. Return **unavailable** separately from confirmed air. |
| Target selection | Use the [exact identifier list](../../include/ore_outline/block_esp.hpp), defaulting to normal and deepslate diamond ore. Compare copied names, not hashes or runtime IDs. Port the [script's sticky selection](../../probes/loaded-diamonds/scripts/tracer.js) to a small set of nearby targets. Recheck that set at a bounded cadence so mined, replaced, unloaded, or out-of-window targets clear or retarget. The scan and frame paths exchange values, not `Block`, chunk or player pointers. |
| Main world frame | Copy a coherent camera and viewport from the frame actually rendered, including any camera-relative origin and render-viewport-to-HUD transform. Normalize it to the [portable clip convention](../../include/ore_outline/core.hpp). Project a line and a solid silhouette per selected target, according to the independent toggles. The HUD is composited above the game, so stone cannot occlude them and no depth or terrain change is needed. Don't draw an endpoint behind the camera. No scan work here. |

The [host scheduler](chunk-scanner.md) is reusable **if** the adapter provides its current ready-section feed and a stamp covering hidden block edits and reloads. Without that stamp, do not scan each section once and call it current. A bounded rolling scan over verified loaded cells plus guarded target rechecks can replicate the script's behavior without claiming renderer membership. Start with a measured native budget; one script volume query is not equivalent to a thousand native point reads. Neither Apollon's remesh nor the passive probe's cache of historical positives can seed a current scan of already-loaded blocks.

Pin the binding to the [observed Build ID](intake.md#loaded-build-id) and verify the relevant code/dispatch sites before enabling it. A match alone does not prove ownership or lifetime. Only draw when the target and a fresh main-pass camera belong to the same world/dimension session. Clear the HUD batch and invalidate stale snapshots on toggle-off, lost context, pause/exit, or world/dimension change. If the frame producer stops, the retained HUD batch needs an explicit clear or an expiry mechanism; returning no new commands is not enough. Unsupported builds and unproven contexts stay blank.

## Phone checkpoints

First run the [HUD trial](../../README.md#block-esp--chams-hud-trial). The following checks require future builds. Keep Loaded Diamond Scan and the other probes off so they cannot produce a false positive.

1. **Camera only:** Point to one configured block in an offline test world, with zero block-reader calls. Compare the line endpoint and fill to the exposed block, occlude it with stone, rotate and strafe, and check alignment after changing FOV or viewport size. Turn away and check that nothing points behind the eye. Toggle off, pause and leave the world to check cleanup. This proves projection and overlay behavior, not ore detection; mining this fixed marker is not a test of the reader.
2. **Read only:** Repeat the [one-block control](one-block-world-probe.md#device-result) natively: diamond ore → stone → confirmed air at the same loaded position. A distant unavailable position must be rejected with zero block reads. Check unload/reentry and confirm the mod makes no chunk requests or rebuild calls. This proves the controlled read path, not scan coverage.
3. **Combine:** Enable the mod while standing still near several buried ore blocks in previously loaded terrain, with no target XYZ configured and no fresh chunk travel. The matching targets should appear, stay aligned through small moves and turns, and clear or retarget when mined. Switch lines and chams independently, change the identifier list, and check range loss, disable, and leaving or changing dimension. Record scan attempts/time and frame cost with the mod off and on. A working script or passing host tests are not a substitute for this run.

## Narrowed native leads (static only)

These observations are from the [matching Drive ELF](intake.md#binary-intake), not a new phone run. The addresses locate evidence in that sample; they are not an approved hook table, callable symbols or launcher SDK layouts.

- **Camera:** The `InGamePlayScreen` RTTI and RELATIVE relocations tie address point `0x138d39f8` to `0x9f14994` at `+0x98`. Its direct call at `0x9f14c34` reaches `0x9f14dc8`; that path gets the [player camera](render-section-lifecycle.md#which-view-owns-the-grid) at `0x9f14f14`, calls `0xb7cf9e8` at `0x9f14f2c`, and reaches the player/terrain handoff at `0x9f153c8`. `0xb7cf9e8` selects two 64-byte matrix stack tops and can write view/projection data there, with camera-position stores at `0xb7cfcd0..0xb7cfce4`. The candidate in [XRAY-008](xray-008-evidence.md#what-the-report-establishes), `0xb7cf81c`, is reached at `0x9f198f4` in `0x9f1973c` under another path that temporarily sets and restores size-like state (`0x9f18774` and `0x9f187f0`). Do not assume that copy is the main scene or that patching a listed slot observes direct calls. The coherent sampling point, viewport mapping and lifetime still need validation.
- **Read:** The `ScriptDimension::isChunkLoaded(Vec3 const&)` reflection entry leads into a script receiver and position/error machinery (`0xeb030d8..0xeb03180`). The helper at `0xde1fcec` calls a region slot at `+0x138`, then checks the result via `0xf3fe304`; the concrete `BlockSource` slot for that offset routes through `0x1037b334` to `0x10370c80`. The latter is [the cache-mutating lookup from XRAY-008](xray-008-evidence.md#what-the-report-establishes). This is a lead into the engine's checks, not a bare native loaded predicate or a guarantee for a client source. Don't call the reflection thunk or interpret fallback air as loaded air. Separate source candidates are `ChunkViewSource` (`0x13e12d20 + 0x20 → 0x10bee704`, a locked grid lookup) and `NetworkChunkSource` (`0x13e0f480 + 0x20 → 0x10b69130`, a weak-map lookup with ref promotion). A reference protects a chunk's lifetime, not necessarily its section data. The actual local producer, owning update scope, section-data synchronization and non-fallback read still need proof.
- **Type name:** The [XRAY-006 key path](xray-006-evidence.md) is `Block + 0x68 → type + 0xc8`; its hash does not replace an identifier comparison. In the matching ELF, `0x10765c70..0x10765cb4` copies the tagged string via `0x134ef06c`. This supports exact-name matching as a design but is not a device-tested accessor.
