# Render-section lifecycle — Bedrock 1.26.62 ARM64

**Status: static trace and host replay, not a live binding.** The [two-point device trial](passive-terrain.md#device-result) proves selected reads reached both diamond controls. It doesn't prove that a build was adopted, that its section stayed in range, or that every cell was read. This investigation separates those events. Neither LeviPack uses the new host model.

## Which view owns the grid?

**Player path, statically identified.** The `LevelRenderer` constructor installs `LevelRendererPlayer`'s vtable (`0x13a55e10`, store at `0xb794128`) on the object it keeps at `LevelRenderer +0x430` (`0xb795934`). The getter `0xb7a376c` returns that object. The frame path at `0x9f153c8 → 0xb7a1c54` passes it to the player pre-render update (`0xb7a1e14 → 0xb7a2f10`), then enters `LevelBuilder` with the subobject at `LevelRenderer +0x500` (`0xb7a2a68 → 0xb818e3c`). The separate lead `0xb7bfa2c → 0xb7b0390` is inside the player update (`0xb7a2f88 → 0xb7bf9dc`), not the list's acceptance event.

**The list is not player-only.** `0xb818e3c` visits the player and can use auxiliary views via `0xb7a41a8` and `0xb7a41d4` (`LevelRenderer +0x440/+0x450`). In the `0xb819ac0` list path, `0xb81a7c4..0xb81a7cc` and `0xb81b914..0xb81b91c` pass a camera from the builder's array to the grid lookup. On the latter route its returned instance is passed to `0xb81eff4` at `0xb81b8fc`. That helper reads the candidate before the conditional adoption and the active geometry afterward (`0xb81f02c`, `0xb81f05c`, `0xb81f07c`). Merely hitting the helper, or seeing it consult the player getter, does not establish that the **instance** belongs to the player grid or that a swap occurred.

## Build identity and valid cells

- **Worker and completion share a context, not a durable ticket.** On the traced asynchronous route the scheduler copies the same `BuildTaskContext` reference into both payloads (`0xb81dfec`, `0xb81e3dc`). The worker (`0xb825308..0xb825320`) and the completion (`0xb8253e0..0xb8253ec`) use it. Completion can later stage an instance candidate via `0xb82566c → 0xa9d48b8`, which is still not the active geometry install. This narrows the path to correlate; it does not prove cancellation/drain ordering or give the pre-cull cell callback a ticket. Any future correlation must be scoped to a proven lifetime and carry an observer-issued identity through **actual adoption**, without keeping raw engine addresses as persistent keys.
- **A non-null chunk lookup does not certify a valid cell.** The block read at `0x10371934` takes a default-block path for out-of-bounds Y or a missing chunk, but there is another fallback after the chunk lookup succeeds. The per-chunk read `0x10bab9e4` also takes it if the subchunk index is outside the array or the primary block storage is null (`0x10baba24`, `0x10baba3c..0x10baba44`). The normal storage dispatch at `0x10baba84` is separate. All those fallback routes converge on the same default-block getter (`0x1091a034`); the result consumed by the current probe does not say which route ran. Until loaded air can be proven independently within the same ordinary read, ambiguous cells remain unavailable for coverage. No second lookup is justified by this trace.

## Invalidation, range and world lifetime

- **Dirty notification is distinct from adoption.** Coordinator vtable `0x139cf2e0` leads to `0xa9cc944` and `0xa9cd168`. Both compare a dimension value against coordinator `+0x68`, derive signed section XYZ, and set flags on queued coordinate entries (`0xa9cca30`, `0xa9cd248`). The queue consumer at `0xa9cd724` resolves the section (`0xa9cd7b8`) and updates the shared-current and pending geometry's scheduling fields (`0xa9cd80c..0xa9cd824`, `0xa9cd880..0xa9cd890`). The rebuild predicate `0xa9d6a1c` later reads those fields. This is a route to invalidate before a new mesh arrives, not proof that **every hidden edit** travels through it. The geometry version near `+0x26e` is a byte; producer logic at `0xa9d6230..0xa9d625c` masks a successor to eight bits. Neither it nor a pointer is a durable content stamp.
- **World/dimension scope cannot be guessed from XYZ.** The `LevelRenderer` constructor stores its level argument at `+0x3c0` (`0xb793f9c`); its dimension-keyed coordinator lookup at `0xb7a4200` can construct `RenderChunkCoordinator(Level&, LevelRenderer&, DimensionType)` at `0xb7a433c → 0xa9cb7a0`. That constructor stores the two owners and dimension (`0xa9cb848..0xa9cb84c`). This gives ownership leads, not a verified world-switch boundary or a worker drain. A future adapter must issue a fresh world/capture epoch on replacement, dimension change, context loss or disable and reject old reports. It must not key identity by reused engine addresses or use the launcher pause callback as a worker barrier.

## Host replay

[`BuildSamples` and `Sections`](../../include/ore_outline/passive_sections.hpp) model the contract using copied values only. `make test` exercises [simulated builder visits and owner events](../../tests/passive_sections_test.cpp), not an engine adapter:

- Admit a build for a section with a fresh ticket. Count **distinct** valid visits to the 4,096 positions in that section. Clipped/canceled work, missing or fallback cells, and conflicting samples cannot certify coverage. Neighbor visits don't count. The worker has fixed scratch and makes no independent read requests.
- Publish only a sealed, complete report for the current ticket after explicit owner-side adoption and ready/in-range membership. Before adoption, an early report is not retained; an adapter would have to hand it off in bounded storage or drop it. A full, valid build with no ores is `ObservedEmpty`; already meshed but never observed, dropped, superseded and incomplete builds are `Unobserved`. Invalidation or removal drops the prior ticket immediately. Even if coordinates are reused, old tickets can't repopulate the cache.
- The replay discovers ores the collector was never configured with, including neighboring sections across negative X. It grows the fixture from **5 → 22 → 31** chunk columns (two vertical sections each), then drops back to **5**. It tests replacement by stone, out-of-range removal and return, world/dimension changes, sealed late work, and filtering without a rebuild.
- Fixture limits are 1,024 tracked section tickets and 64 retained ore positions per section, with explicit `Truncated` coverage if more matches were seen. Snapshots return at most 256 copied positions, nearest sections first; the overlay's line limit remains a separate gate. These are host limits, not render distances or device timing claims.

## Next validation gate

The [0.2.0 live discovery trial](live-terrain-discovery.md#device-result) found unannounced historical positives across sections using the already scoped read. It does not install an adoption observer or attempt to show current coverage. The separate [Loaded Diamond Scan](loaded-diamond-scan.md) tests stationary discovery in blocks available to world scripting, not render-ready membership.

1. Before reporting **current** sections, establish a safe owner-thread observation for the player view's actual adoption and changing membership. Qualify each instance by the owning view rather than the shared helper. A mod-issued ticket must follow the scoped build to that adoption, not merely to completion. The pre-cull callback supplies a source and XYZ but no build ticket or valid-cell signal. Those signals, dirty/removal coverage (including hidden edits), world/dimension/context teardown, and bounded, synchronized transfer still need independent proof. Do not call private scheduling, rebuild, lookup or release functions to make the diagnostic run.
2. Once those signals are available, measure the lifecycle with a bounded, report-only diagnostic in a disposable offline world. Compare scheduled/built/adopted/in-range/retired observations, without assuming every build is adopted or every visible tile is newly built. Include movement and two render distances, empty and enclosing terrain, an edit during an in-flight rebuild, leaving/reentering range, and a dimension/world change at reused coordinates. If events disagree or overflow, report coverage as unknown and clear stale results.
3. Before drawing on real terrain, verify live discovery, stale-result removal, and bounded observer cost on device. Camera/viewport coherence is a separate gate. The static trace and host replay don't validate any of these device outcomes.
